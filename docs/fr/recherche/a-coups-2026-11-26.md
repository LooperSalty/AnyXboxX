# Pics de temps d'image et pression mémoire, 26/11/2026

Piste de performance n° 3 : les à-coups (images isolées de 100 à 360 ms) et la pression mémoire qui empêchent de tenir 30 fps constants. Machine : RTX 4070 SUPER (12 Go, budget DXGI d'environ 10,6 Go), i7-13700KF, 32 Go de RAM, profil Series X.

Version anglaise : `docs/research/stutter-2026-11-26.md`.

## Méthode

- **Source.** Cinq journaux de jeu du jour, les plus longs et les plus récents : `game-1795703210`, `game-t5fxceless`, `game-t6confirm`, `game-t7alt`, `game-t8wideplan` (dans `%LOCALAPPDATA%\AnyXboxX\logs\`, codes ANSI retirés). Mesuré : nous avons lu les journaux nous-mêmes. Aucune donnée du jeu n'est copiée dans le dépôt ; seuls des comptes et des sommes figurent ici.
- **Unité de mesure.** Le journal écrit une ligne par fenêtre d'environ 5 s (`N fps, X ms/frame (préparation : ...; sur le GPU ...; recopie ...; passes du tas de buffers Y ms; abandonnés Z sans pipeline hôte)`). La fenêtre est la moyenne de ces images. **Une fenêtre ne montre pas une image isolée de 100 à 360 ms.** Les chiffres de 100 à 360 ms de la piste viennent de la mesure de temps d'image hors de ces journaux (PresentMon), pas d'eux (supposé, non vérifié ici). Ce qui suit porte sur les fenêtres dont la moyenne dépasse 100 ms par image.
- **Comptes.** 304 fenêtres dans les cinq essais, dont 65 (21 %) dépassent 100 ms par image en moyenne (mesuré par script : 12, 13, 11, 16, 13 par essai). Fenêtre médiane : 61,8 à 72,3 ms selon l'essai. Pire fenêtre : 7 224 ms (`game-t5fxceless`, dont 2 884 ms sur le GPU).
- **Répartition.** Pour chaque fenêtre : images = fps × durée de fenêtre ; temps perdu = images × (ms/frame − 33,3) (mesuré par script). Catégories de coût = images × ms par image de la catégorie, telles qu'imprimées par la ligne de fenêtre (mesuré ; les catégories se recouvrent, ce n'est pas une partition exacte).
- **Corrélations.** Par fenêtre, événements survenus dans la fenêtre (lignes comptées par script). Corrélation, pas causalité.

## Classement des causes

1. **Passe sur le tas (148 s, 43 % du temps perdu).** La passe marquée (`VICTORY_HEAP_PASS_DIRTY=1`, déjà dans `TUNED`) compare encore l'enregistrement de chaque emplacement gardé à chaque passe : `heap_pass.rs` lance `plan()` avec `scan_every`, et `VICTORY_HEAP_SCAN_EVERY` vaut 1 par défaut dans le code. Le commentaire de documentation disait 16 ; le code dit 1. La ligne des descripteurs annonce 164 000 à 227 000 emplacements examinés par image (mesuré). Correctif tenté : `VICTORY_HEAP_SCAN_ALT` (voir plus bas).
2. **Recopie vers le PC (55 s, 16 %).** Environ 57 Mo par fenêtre dans les fenêtres à pics. Non traité sur cette branche.
3. **Copies hôte préparées sur le thread de soumission (39 s, 11 %).** Environ 177 Mo par fenêtre dans les fenêtres à pics. Non traité.

Second rang, non chiffré en temps dans le journal : premières liaisons de nouveaux pipelines et dessins abandonnés pendant que leur pipeline n'est pas prêt (`VICTORY_PIPELINE_WAIT_MS=2500` dans `TUNED`) ; requêtes dstorage lentes ; remappages de mémoire du titre ; rafraîchissements de textures.

## Ce que les journaux ne soutiennent pas

- **L'hypothèse « carte pleine ».** « The texture queue is refused, the card has no room » apparaît 176 fois dans les fenêtres à pics et 3,4 fois par fenêtre dans les fenêtres calmes : aucune différence (mesuré). Le budget est passé de 11 229 Mo à 10 316 Mo une fois dans `game-t8wideplan` (mesuré), sans que les fenêtres à pics s'en distinguent. Un budget lu par `QueryVideoMemoryInfo` peut aider lors des changements de budget, mais n'explique pas les pics dans ces journaux.
- **Série mémoire (RAM).** Les journaux ne donnent la RAM qu'aux changements de budget (« 9 884 Mo de la carte et 4 664 Mo de la mémoire partagée du PC en usage » dans `game-t8wideplan`). Il n'y a pas de série temporelle de commit ni de RAM, donc le chiffre 27,8 sur 32 Go ne peut pas être relié aux pics ici (non mesuré).

## Correctif de cette branche

`VICTORY_HEAP_SCAN_ALT` dans `crates/victory-gpu/src/heap_pass.rs` (désactivé par défaut, rien n'est ajouté à `TUNED`) :

- `1` : le balayage de tous les emplacements gardés a lieu toutes les 16 passes au lieu de chaque passe ;
- `alt` : vingt secondes en balayage lent, vingt secondes en balayage par défaut, en alternance, chaque bascule écrite dans le journal ;
- absent ou `0` : inchangé.

Compromis : un enregistrement modifié hors API n'est vu que jusqu'à 15 passes plus tard (environ 0,5 s à 30 fps). Un descripteur périmé pourrait dessiner l'ancienne texture pendant ce temps. C'est pourquoi l'option est désactivée par défaut.

Tests (mesuré, `cargo test --release -p victory-gpu`) : les deux nouveaux tests unitaires de la phase lente passent (filtre `heap_pass` : 6 réussis). Crate complet : 238 réussis, 3 échecs, 4 ignorés ; les 3 échecs sont les tests WARP connus de main (`spans_say_the_next_start_and_the_lowest_level_viewed`, `warp_card_patch_writes_the_masked_bytes_and_no_others`, `warp_card_fetch_copies_flagged_pieces_to_their_slots`), aucun nouvel échec. `cargo xtask policy` : 214 fichiers conformes. Build release de `victory` : réussi.

**Non mesuré :** que `VICTORY_HEAP_SCAN_ALT=alt` réduise les pics. Il faut un essai en jeu (`--override VICTORY_HEAP_SCAN_ALT=alt`, puis comparer les fenêtres `ms/frame` des deux phases dans le même journal). Non lancé ici, la tâche interdit de lancer le jeu.
