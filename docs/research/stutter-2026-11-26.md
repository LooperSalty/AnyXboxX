# Frame-time spikes and memory pressure, 2026-11-26

Performance track 3: the spikes (single frames of 100 to 360 ms) and the memory pressure that keep the game from holding a constant 30 fps. Machine: RTX 4070 SUPER (12 GB, DXGI budget about 10.6 GB), i7-13700KF, 32 GB RAM, Series X profile.

## Method

- **Source.** Five game logs of the day, the longest and most recent: `game-1795703210`, `game-t5fxceless`, `game-t6confirm`, `game-t7alt`, `game-t8wideplan` (`%LOCALAPPDATA%\AnyXboxX\logs\`, ANSI codes stripped). Measured: we read the logs ourselves. No game data is copied into the repository; only counts and sums appear here.
- **Unit of measure.** The log writes one line per window of about 5 s (`N fps, X ms/frame (preparing: ...; on the GPU ...; copying back ...; heap buffers ... passes Y ms; dropped Z without a host pipeline)`). The window is the average over those frames. **A window cannot show a single 100 to 360 ms frame.** The 100 to 360 ms figures of the track come from frame timing outside these logs (PresentMon), not from them (assumed, not checked here). What follows is about windows whose average is above 100 ms.
- **Counts.** 304 windows in the five runs, of which 65 (21 %) average above 100 ms per frame (measured by script: 12, 13, 11, 16, 13 per run). Median window: 61.8 to 72.3 ms per run. Worst window: 7 224 ms (`game-t5fxceless`, one window with 2 884 ms on the GPU).
- **Attribution.** For each window: frames = fps times window length; lost time = frames times (ms/frame minus 33.3) (measured by script). Cost categories = frames times the category's ms per frame, as printed by the window line (measured, the categories overlap the frame, they are not an exact partition).
- **Correlations.** Per window, events in the window before the line (log lines counted by script). Correlation, not causation.

## Ranking of causes

1. **Pass over the heap (148 s, 43 % of the lost time).** The marked pass (`VICTORY_HEAP_PASS_DIRTY=1`, already in `TUNED`) still compares the record of every kept slot in every pass: `heap_pass.rs` runs `plan()` with `scan_every`, and `VICTORY_HEAP_SCAN_EVERY` defaults to 1 in the code. The doc comment said 16; the code says 1. The descriptor line reports 164 000 to 227 000 slots looked at per frame (measured). Fix attempted: `VICTORY_HEAP_SCAN_ALT` (see below).
2. **Copying back to PC (55 s, 16 %).** About 57 MB per window in the spike windows. Not addressed in this branch.
3. **Host copies prepared on the submitting thread (39 s, 11 %).** About 177 MB per window in the spike windows. Not addressed.

Secondary, not quantified as time in the log: first binds of new pipelines and the draws dropped while their pipeline is not ready (`VICTORY_PIPELINE_WAIT_MS=2500` in `TUNED`); slow dstorage requests; title memory remaps; texture refreshes.

## What the logs do not support

- **The card-full theory.** "The texture queue is refused, the card has no room" appears 176 times in the spike windows and 3.4 per window in the calm ones: no difference (measured). The budget moved from 11 229 MB to 10 316 MB once in `game-t8wideplan` (measured), and the spike windows do not stand out for it. A budget read from `QueryVideoMemoryInfo` may still help with the budget changes, but it does not explain the spikes in these logs.
- **Memory (RAM) series.** The logs give RAM only at budget changes ("9 884 MB of the card and 4 664 MB of the PC's shared memory in use" in `game-t8wideplan`). There is no time series of commit or RAM in the logs, so the 27.8 of 32 GB figure cannot be linked to the spikes here (not measured).

## Fix in this branch

`VICTORY_HEAP_SCAN_ALT` in `crates/victory-gpu/src/heap_pass.rs` (off by default, nothing added to `TUNED`):

- `1`: the scan of every kept slot runs every 16 passes instead of every pass;
- `alt`: twenty seconds in the slow scan, twenty seconds in the default, in turn, each change written to the log;
- unset or `0`: unchanged.

Trade-off: a record changed past the API is seen up to 15 passes later (about 0.5 s at 30 fps). A stale descriptor could draw the old texture for that time. That is why it is off by default.

Tests (measured, `cargo test --release -p victory-gpu`): the two new unit tests of the slow phase pass (`heap_pass` filter: 6 passed). The full crate: 238 passed, 3 failed, 4 ignored; the 3 failures are the known WARP tests on main (`spans_say_the_next_start_and_the_lowest_level_viewed`, `warp_card_patch_writes_the_masked_bytes_and_no_others`, `warp_card_fetch_copies_flagged_pieces_to_their_slots`), no new failure. `cargo xtask policy`: 214 files ok. Release build of `victory`: ok.

**Not measured:** whether `VICTORY_HEAP_SCAN_ALT=alt` reduces the spikes. That needs a game run (`--override VICTORY_HEAP_SCAN_ALT=alt`, then compare the `ms/frame` windows of the two phases in the same log). It was not run here, as the task forbids launching the game.
